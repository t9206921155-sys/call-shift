1. Общие сведения

1.1. Назначение документа

Документ определяет полный объём требований к приложению, которое перехватывает входящий вызов на уровне Android Telecom Framework и перенаправляет его по заданному правилу — на другой номер, на SIP-аккаунт или на оператора связи (сеть), а также уведомляет пользователя о факте вызова.

Документ является основанием для:

  • оценки трудозатрат и составления плана работ;
  • разработки архитектуры и кода;
  • приёмки результата (см. раздел 18 «Критерии приёмки»).

1.2. Ключевое проектное решение, зафиксированное заказчиком

Параметр Решение
Механика Перехват и перенаправление звонков (CallScreeningService + ConnectionService), а не только MMI-коды оператора
Стек Выбирает исполнитель (рекомендация — нативный Kotlin)
Масштаб Личное использование, установка через adb/sideload, максимум возможностей, включая сценарии с ADB-грантами и root
Формат поставки APK + исходный код + ТЗ + инструкции

1.3. Термины и сокращения

Термин Определение

2. Границы проекта (Scope)

2.1. В объёме работ (In scope)

  1. Движок правил переадресации с приоритетами, условиями и расписанием.
  2. Перехват входящих вызовов через CallScreeningService (режим «экран screening-приложения»).
  3. Режим «полного телефона»: приложение как default dialer (ROLE_DIALER) с собственным InCallService — даёт максимальные полномочия в Telecom.
  4. Четыре стратегии перенаправления (см. 3.3): сеть (MMI), callback-дозвон, SIP/VoIP, уведомление-эскалация.
  5. Управление сетевой переадресацией через MMI/USSD с отображением статуса по каждой SIM.
  6. Журнал событий переадресации (локальная БД), уведомления, быстрый тайл/виджет.
  7. Инсталлятор-мастер: проверка и выдача ролей/разрешений через adb (скрипт) и через системные настройки (ручной путь).
  8. Сборка, подписание и поставка APK; CI-конвейер; инструкция по установке на устройство.
  9. Комплект документации: README, инструкция установки, инструкция ADB-настройки, known issues по OEM.

2.2. Вне объёма (Out of scope), если не заказано отдельно

  • Публикация в Google Play / RuStore и прохождение их политик (раздел 7.4 описывает ограничения).
  • Бэкенд, личный кабинет, биллинг, мультипользовательность.
  • Запись разговоров в файл (в объёме только транзит аудио; запись — отдельная задача с отдельными юридическими рисками).
  • Интеграция с конкретными CRM/1С/контакт-центрами.
  • Поддержка iOS.
  • Локализация на языки, кроме RU/EN.

3. Постановка задачи

3.1. Проблема

Штатные средства Android дают пользователю только «всё или ничего»: системная переадресация спрятана в настройках телефона, требует ручного ввода MMI-кодов, не зависит от условий (время, номер, SIM, занятость), не ведёт журнала и не умеет комбинировать сценарии «отклонить + позвонить на другой номер» или «отправить в SIP».

3.2. Цель

Единое приложение, которое по declarative-правилам решает судьбу каждого входящего вызова за время, не заметное пользователю, и обеспечивает один из исходов:

  1. пропустить вызов как обычно;
  2. отклонить/заглушить и перенаправить на целевой номер (callback-лег);
  3. включить/выключить сетевую переадресацию на стороне оператора (работает даже при выключенном телефоне);
  4. принять вызов и транслировать его в SIP (мост GSM ↔︎ VoIP);
  5. уведомить пользователя/внешнюю систему о вызове, не мешая разговору.

3.3. Стратегии перенаправления — обязательная таблица выбора

Исполнитель реализует стратегии как сменные модули за общим интерфейсом ForwardStrategy. Выбор стратегии — в правиле.

ID Стратегия Как работает Что видит звонящий Что видит владелец Зависимости Приоритет реализации
S1 Сетевая CF (MMI) Приложение набирает *21*<номер># / *61*… / *67*… через TelecomManager.placeCall без UI; переадресацию выполняет сеть оператора Слышит гудки и попадает на целевой номер; виден реальный номер владельца Телефон может быть выключен — переадресация всё равно работает Поддержка оператором; только на уровне сети; нет гибких условий «по приложению» M1
S2 Screening + callback-дозвон CallScreeningService отклоняет вызов (setDisallowCall(true) + setRejectCall(true)), затем приложение совершает исходящий звонок на целевой номер Вызов сбрасывается (или уходит в «пропущенные»), затем ему перезванивает владелец — либо владелец звонит на целевой номер Видит уведомление «вызов перехвачен → дозвон на X» Роль ROLE_CALL_SCREENING; разрешение CALL_PHONE; не является «настоящей» переадресацией — это переадресация через приложение M1 (основная)
S3 SIP/VoIP-мост Входящий GSM-вызов принимается, параллельно поднимается SIP-плеер через self-managed ConnectionService; аудио связывается мостом Говорит с абонентом SIP (или слышит голос владельца через мост) Может слушать/говорить через SIP-приложение SIP-стек (PJSIP/linphone-sdk), MANAGE_OWN_CALLS, стабильный интернет M3
S4 Уведомление / эскалация Вызов пропускается, но факт вызова и метаданные отправляются в Telegram/webhook/на второй телефон Обычный звонок Мгновенное уведомление с кнопками «перезвонить», «переадресовать», «заблокировать» INTERNET, POST_NOTIFICATIONS M2

Обязательное требование к честности продукта. В UI и в документации приложение должно явно различать S1 («реальная сетевая переадресация») и S2 («перехват и дозвон на уровне приложения»). Пользователь должен понимать: S2 не передаёт исходный номер звонящего целевому абоненту по сети — GSM не позволяет подменить CLI сторонним приложением. Компенсационное решение — раздел 10.6 (передача номера через DTMF/голосовое приветствие/SIP-заголовок P-Asserted-Identity в S3).

Обозначения приоритета: M — must (обязательно для приёмки), S — should, C — could.

4.1. Правила переадресации

6.3. Ключевые интерфейсы (контракт для разработчика)

// domain/ForwardStrategy.kt
interface ForwardStrategy {
    val id: StrategyId           // S1_MMI | S2_CALLBACK | S3_SIP | S4_NOTIFY | BLOCK | PASS
    suspend fun execute(ctx: CallContext): ForwardResult
    fun isAvailable(profile: PermissionProfile): Boolean   // деградация по профилю A/B/C
}

// domain/CallContext.kt
data class CallContext(
    val rawHandle: String?,          // может быть null (скрытый номер)
    val e164: String?,               // нормализованный
    val direction: Direction,        // INCOMING | OUTGOING
    val phoneAccount: PhoneAccountRef?, // SIM
    val isEmergency: Boolean,
    val isSelfManaged: Boolean,
    val timestampEpochMs: Long,
    val extras: Map<String, String>
)

// domain/RuleEngine.kt
interface RuleEngine {
    suspend fun evaluate(ctx: CallContext): Decision   // < 3000 мс, fail-open
}
data class Decision(
    val verdict: Verdict,            // PASS | DISALLOW_REJECT | DISALLOW_AS_MISSED | SILENCE
    val strategy: StrategyId?,
    val target: String?,
    val ruleId: Long?,
    val reason: String,              // для журнала и отладки
    val screeningResponse: ScreeningFlags
)

6.4. Потоки и конкурентность

  • Все suspend-функции — на Dispatchers.Default (логика) и Dispatchers.IO (БД/сеть).
  • Screening-сервис живёт в основном процессе приложения; для минимизации cold start — не выносить в отдельный процесс (иначе каждый вызов платит за старт процесса).
  • Долгие операции (дозвон, SIP-мост, webhook) — в ForwardDispatcher, запускаемом через foreground-сервис type="phoneCall" (Android 14+ требует явного типа FGS).
  • Единая точка сериализации событий — Actor-подобная очередь (Channel), чтобы два одновременных входящих не устроили гонку дозвона.

events (журнал) Room индекс по timestamp, TTL-очистка WorkManager'ом

settings DataStore Preferences типизированный wrapper
secrets (SIP-пароли, токены) EncryptedSharedPreferences / Keystore никогда не в Room и не в экспорте без пароля

7.2. Роли и команды настройки (профиль B — рекомендуемый)

Установка через adb (входит в поставку как scripts/setup_device.sh):

PKG=fi.callshift.app

# 1) Установка APK
adb install -r -t app-release.apk

# 2) Runtime-разрешения без диалогов
for p in READ_PHONE_STATE READ_PHONE_NUMBERS CALL_PHONE ANSWER_PHONE_CALLS \
         READ_CALL_LOG WRITE_CALL_LOG READ_CONTACTS POST_NOTIFICATIONS; do
  adb shell pm grant $PKG android.permission.$p || true
done

# 3) Роль screening-приложения (перехват входящих)
adb shell cmd role add-role-holder --user 0 android.app.role.CALL_SCREENING $PKG

# 4) Роль dialer (полный контроль Telecom; требует реализованных Dialer/InCallService)
adb shell cmd role add-role-holder --user 0 android.app.role.DIALER $PKG
# проверка:
adb shell cmd role get-role-holders --user 0 android.app.role.DIALER

# 5) Исключение из оптимизации батареи
adb shell dumpsys deviceidle whitelist +$PKG

# 6) (Xiaomi/OEM) автозапуск — только вручную в настройках оболочки, см. 11.5

Откат:

adb shell cmd role remove-role-holder --user 0 android.app.role.CALL_SCREENING $PKG
adb shell cmd role remove-role-holder --user 0 android.app.role.DIALER $PKG
adb shell pm revoke $PKG android.permission.ANSWER_PHONE_CALLS

Требование FR-P2: приложение должно уметь показать эти команды внутри UI (экран «Диагностика») и проверить результат после их выполнения (кнопка «Перепроверить»).

Требование FR-P3: при назначении ROLE_DIALER системный dialer заменяется — приложение обязано реализовывать минимально пригодный dialer (набор номера, экран входящего/активного вызова, ответ/отбой), иначе пользователь останется без телефона. Это требование — самая дорогая часть профиля B, оценка в разделе 17.

Требование FR-P4: при первом запуске без ролей приложение не должно «молча не работать»: показывать баннер «Перехват не активен» и вести в мастер настройки.

7.3. Ручной путь (без adb)

Настройки → Приложения → Приложения по умолчанию → Телефон / Определение номера и спам-фильтр (Call screening) → выбрать CallShift. Пункты меню различаются по OEM — документировать скриншотами для каждой оболочки (раздел 11.5).

7.4. Ограничения Google Play (справочно, т. к. проект — sideload)

Если в будущем потребуется публикация:

  • приложение с CallScreeningService обязано объявить в manifest <uses-permission android:name="android.permission.CALL_SCREENING"/> и пройти проверку декларации;
  • политика Play запрещает приложения, чья основная функция — перенаправление вызовов без согласия оператора/пользователя, а также «call forwarding» как основной сценарий для немодерируемого распространения;
  • роль default dialer требует декларации MANAGE_OWN_CALLS/ANSWER_PHONE_CALLS и видео-демонстрации;
  • публикация в Play не входит в объём данного ТЗ; при заказе — отдельная задача с аудитом политик.

8.3. Состояния (state machine) главного экрана

NOT_CONFIGURED → PARTIAL (есть роль screening, нет разрешений) → ACTIVE → SUSPENDED (мастер-выключатель) → ERROR (роль отозвана системой)

Переход в ERROR обязан порождать уведомление «Переадресация не работает: роль отозвана» — частый сценарий после обновления OEM-оболочки.

10. Алгоритмы

10.1. Нормализация номера

  1. Получить Call.Details.getHandle() → tel: URI → строка.
  2. null/пусто → anonymous = true, e164 = null.
  3. PhoneNumberUtil.parse(raw, defaultRegion) → format(E.164).
  4. Дополнительно хранить national и e164 для матчинга (оператор может отдать номер в национальном формате).
  5. Маски: поддержка * (префикс/суффикс) и ? (цифра); сравнение — по нормализованной строке; недопустимые маски отклоняются при сохранении.

10.2. Матчинг правил

вход: CallContext
1. if ctx.isEmergency → Decision(PASS, reason="emergency")   // абсолютный приоритет
2. if !settings.masterEnabled → Decision(PASS, reason="master_off")
3. rules = repo.enabledRulesSortedByPriority()               // кэш в памяти, инвалидация по Flow
4. for rule in rules:
     if rule.schedule.matches(now) && rule.conditions.matches(ctx) → return Decision(rule)
5. return Decision(defaultPolicy)
Ограничение: весь цикл ≤ 3000 мс; при TimeoutException → PASS + событие "engine_timeout"

Кэш контактов: предзагрузка множества нормализованных номеров в HashSet при старте процесса и по ContentObserver; при размере > 20 000 — переход на Room-запрос по индексу.

10.3. Антипетля и антишторм (обязательно)

Guard Правило Действие при срабатывании
Loop-self target == callerNumber отклонить правило, событие guard_loop
Loop-owner target == ownNumber(SIM) то же
Loop-recursion входящий от target при активном правиле с тем же target пропустить вызов (PASS), событие guard_recursion
Storm > N дозвонов за T PASS + уведомление «сработала защита от шторма»
Cooldown тот же номер дважды за < 30 с второе событие — PASS
Cost номер цели в премиум-диапазоне (список по стране) запрос подтверждения в настройках правила

10.4. Работа с MMI

buildMmi(service, target, noReplySec, mode) →
  REGISTER:  "*<code>*<target>#", для 61: "*61*<target>**<sec>#"
  ERASE:     "##<code>#"
  INTERROGATE: "*#<code>#"
  ERASE_ALL: "##002#"
send: TelecomManager.placeCall(phoneAccountHandle, Uri.parse("tel:<mmi>"), extras)
      fallback: Intent.ACTION_CALL (профиль A без placeCall)
result: ResultReceiver → разбор текста USSD (best-effort, по локали оператора) → cf_state.actual_*

Требование: коды отправлять именно на нужный SIM-account (PhoneAccountHandle из TelecomManager.getCallCapablePhoneAccounts()), иначе на двухсимочных устройствах настройка уйдёт не на ту SIM.

10.7. Аудио-мост (S3 / M4) — уровни возможности

Уровень Условие Что доступно
L0 Сток, профиль A/B Только «слепая» переадресация без моста: GSM-вызов отклоняется, SIP-плеер звонит цели. Аудио не связывается

11. Выживаемость и борьба с ограничениями OEM

11.1. Общие меры

  1. CallScreeningService вызывается системой — он не подвержен обычному kill'у процесса, но холодный старт процесса платит за инициализацию → требование: инициализация ленивая, без тяжёлых библиотек в Application.onCreate (DI-граф — lazy, SIP-стек — только в M3 и только по требованию).
  2. Foreground service type="phoneCall" — только на время активной фазы (дозвон/мост), с корректным stopSelf.
  3. WorkManager для отложенных задач (retry webhook, очистка журнала, периодическая сверка cf_state — не чаще 1 раза в 6 ч).
  4. Исключение из battery optimization (ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS + adb deviceidle whitelist).
  5. BOOT_COMPLETED → восстановление desired state, повторная проверка ролей.
  6. Watchdog: JobScheduler-задача раз в 6 ч проверяет наличие ролей; при потере — уведомление.

11.3. Конфликт с системными screening-приложениями

Требование FR-S1: на устройствах, где роль CALL_SCREENING уже занята (например, Google Phone / Mi Dialer), установка нашей роли отзывает предыдущую — приложение должно предупредить об этом в onboarding и предложить возврат (команда adb shell cmd role remove-role-holder).

Требование FR-S2: если пользователь держит системный спам-фильтр, наш движок правил должен учитывать, что часть вызовов может быть отфильтрована до нас — документировать, а не «бороться».

12. Обработка ошибок и краевые случаи

№ Ситуация Ожидаемое поведение
E-01 Screening-роль отозвана системой/пользователем Уведомление «перехват неактивен», статус ERROR, предложение команды восстановления
E-02 Не выдан READ_CONTACTS, правило его требует Правило помечается «деградировано», условие трактуется как «не в контактах» с явной пометкой в журнале; вызов не блокируется ошибкой
E-03 Скрытый номер (handle == null) Ветка «анонимный вызов»; если нет правила — политика по умолчанию
E-04 Экстренный номер Всегда PASS, событие в журнал не пишется (приватность), кроме отладочного уровня
E-05 Второй входящий во время дозвона цели Новый вызов обрабатывается независимо; дозвон прерывается по guard «cooldown»; в журнал — superseded
E-06 Входящий во время активного разговора (занято) Учитывать условие line_state; MMI-код 67 — только через S1
E-07 Нет сети при отправке MMI Retry ≤ 2, затем ошибка NO_NETWORK, desired state остаётся «ожидает применения», задача в WorkManager
E-08 Оператор не поддерживает код (USSD-ошибка) Понятное сообщение + предложение альтернативы (S2)
E-09 Цель недоступна (дозвон не удался) Уведомление, повтор по кнопке, событие DIAL_FAILED с причиной из InCallService/Call.State
E-10 Роуминг По умолчанию — предупреждение о стоимости дозвона цели (guard Cost)
E-11 VoWiFi / VoLTE вызов Поведение screening то же; MMI может быть недоступен → fallback S2
E-12 Вызов из другого приложения (self-managed: WhatsApp/Telegram) По умолчанию не перехватывается (isSelfManaged), настраивается
E-13 Режим «Не беспокоить» Screening продолжает работать (система вызывает сервис), но дозвон цели может быть подавлен DND → предупреждение в UI
E-14 Обновление приложения при активной роли Роли сохраняются; миграции БД обязаны быть обратно совместимыми; проверка в CI
E-15 Смена SIM/eSIM, удаление SIM cf_state помечается stale; правила с селектором HANDLE:<id> — перепривязка по PhoneAccountHandle.id, не по индексу; если id прочитать не удалось (ограничение платформы, FR-2.5) — правило трактуется как «любая SIM»
E-16 Пользователь удалил приложение, CF в сети осталась В onboarding/README — обязательное предупреждение: перед удалением выполнить «Режим паники» (##002#); при удалении через ACTION_PACKAGE_FULLY_REMOVED приложение уже не может ничего сделать — документировать
E-17 Часы устройства сдвинуты / смена TZ Расписание считается в локальной TZ с фиксацией ZoneId; при смене TZ — пересчёт
E-18 Переполнение журнала Ротация: при > 50 000 записей удалять старейшие

19. Приложение A. Справочник MMI-кодов (GSM/3GPP TS 22.082, 27.007)

Сервис Код Установка Снятие Запрос статуса
Безусловная переадресация (CFU) 21 *21*<номер># ##21# *#21#
Переадресация по занятости (CFB) 67 *67*<номер># ##67# *#67#
По недоступности (CFNRc) 62 *62*<номер># ##62# *#62#
По отсутствию ответа (CFNRy) 61 *61*<номер>**<сек># ##61# *#61#
Все условные 002 — ##002# —
Все переадресации 04 — ##04# —
Регистрация/деактивация/стирание/запрос (общий синтаксис) — *<код>*<номер># #<код># / ##<код># *#<код>#
Ожидание вызова (Call Waiting) 43 *43# #43# *#43#
Определение номера (CLIP/CLIR) 30/31 *31# (скрыть) #31# *#31#

Примечания:

  1. Времена для CFNRy: допустимые значения зависят от оператора (обычно 5, 10, 15, 20, 25, 30 с).
  2. Некоторые операторы требуют формат *21*<номер># с номером в международном формате; другие принимают национальный. Требование FR-3.3: всегда E.164.
  3. ##002# — «снять все условные переадресации»; рекомендуется в «Режиме паники» вместе с ##21#.
  4. На VoLTE/eSIM часть кодов может обрабатываться иначе или возвращать ошибку — проверять в M0 на SIM заказчика.

23. Приложение E. Ограничения публичного Android SDK, выявленные при разработке референс-сборки

Раздел добавлен по итогам сборки M0/M1. Все пункты обязательны к учёту исполнителем: они меняют способ реализации, но не меняют функциональные требования.

№ Ограничение Следствие Обход (реализован в референс-сборке)
P-1 CallScreeningService.respondToCall(Call.Details, CallResponse) — первый параметр объект Call.Details, а не строковый callId Наивная реализация «по документации из интернета» не компилируется Сохраняем Call.Details из колбэка и передаём его же в respondToCall
P-2 Call.Details.getPhoneAccountHandle() — @hide/@SystemApi Стороннее screening-приложение не видит, на какую SIM пришёл звонок Reflection → extras → «не определено» (fail-open). Полное решение — профиль B (ROLE_DIALER)
P-3 PhoneAccountHandle.id — @hide Нельзя напрямую сопоставить SIM и правило Reflection к полю id, fallback — разбор toString() ([pkg] id)
P-4 CallResponse.Builder.setRejectedAsMissed() и setSilenceCall() отсутствуют/скрыты в части версий SDK Нельзя полагаться на прямые вызовы Reflection invokeIfAvailable(...) + мягкая деградация с записью в журнал
P-5 Call.Details.PROPERTY_EMERGENCY_CALLBACK — @hide Прямая проверка недоступна Чтение константы через reflection по имени; базовая проверка — нормализатор + локальный список коротких номеров (FR-2.6)
P-6 Публичная сигнатура TelecomManager.placeCall(Uri, Bundle) — без отдельного параметра PhoneAccountHandle Выбор SIM «в лоб» не компилируется EXTRA_PHONE_ACCOUNT_HANDLE в Bundle (литерал "android.telecom.extra.PHONE_ACCOUNT_HANDLE")
P-7 TelecomManager.EXTRA_RESULT_RECEIVER и EXTRA_USSD_RESPONSE — @hide Приём ответа USSD через константы недоступен Строковые литералы ключей; ResultReceiver с onReceiveResult (API 28+, требуется ANSWER_PHONE_CALLS)
P-8 TelecomManager.getDefaultCallScreeningApp() — @SystemApi На Android 9 (API 28) проверить роль нельзя RoleManager на API 29+; на API 28 — только профиль B (см. D1)
P-9 PhoneNumberUtil.isEmergencyNumber() отсутствует в публичном API libphonenumber Проверка экстренных номеров «библиотечным» способом невозможна Локальный набор коротких номеров + префиксов 112/911 (FR-2.6); в M2 — сверка с CarrierConfig
P-10 Kotlin-тесты с не-ASCII именами ломают сборку на JVM с не-UTF-8 sun.jnu.encoding (InvalidPathException) CI падает на этапе compileUnitTestKotlin Имена тестов — ASCII; в gradle.properties заданы systemProp.sun.jnu.encoding=UTF-8 и systemProp.file.encoding=UTF-8
P-11 setSkipCallLog() игнорируется системой для сторонних приложений; вызовы всё равно пишутся в CallLog с типом BLOCKED_TYPE «Скрыть след» в системном журнале нельзя Документируем в UI; собственный журнал событий (FR-7.1) — источник правды

Практический вывод для заказчика. Пункты P-2, P-3, P-5 и P-11 означают, что «максимум возможностей» на стоковом устройстве достигается только в профиле B (ROLE_DIALER, ТЗ п. 3.5 и FR-P3) либо в профиле C (root). В профиле A приложение корректно перехватывает и отклоняет вызовы, выполняет сетевую переадресацию MMI и callback-дозвон, но не различает SIM и не может скрыть запись в системном журнале.
