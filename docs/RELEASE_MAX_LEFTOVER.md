# CallShift 0.8.55-leftover — свой остаточный черновик больше не блокирует MAX навсегда

Полевое наблюдение (OPPO CPH2701, Android 36, MAX 0.8.54-one-place, versionCode 86):
на экране «Мессенджеры» MAX — «● Готов — кнопка обучена, режим включён», но каждый
сценарий отвечает отказом:

```
01.10 18:45 [MAX_UI_REPLY] BLOCKED: В чате есть черновик или MAX не обозначил
подсказку как подсказку. Поле не изменено; смотрите Editor flags в отчёте
```

и так каждую минуту (18:45, 18:46, 18:47, 18:57, 18:58). Выше в том же журнале —
прерванные сценарии, которые сами оставили текст в переписке: «Нажатия не было;
проверьте черновик» (живая проверка), «Черновик оставлен» (нет кнопки отправки) и
автоввод «Тест обучения CallShift» при обучении.

## Причина

Прерванный прогон оставляет в поле сообщения СВОЙ текст: запись прошла, а отправка
не состоялась. MAX при следующем запуске восстанавливает именно этот чат, и сценарий
сразу видит непустое поле. В 0.8.36-send-training-v14 этот разрыв уже лечили, но
только для черновика, побайтно равного тексту ТЕКУЩЕГО прогона. Как только текст
прошлой проверки, текст ответа по правилу или «Тест обучения CallShift» перестали
совпадать с текущим, лечение перестало работать: черновик не очищался никогда.
Пользователь зациклен — живой ответ на звонок не пройдёт, пока он вручную не удалит
чужой на вид текст, а сообщение об отказе этого не говорило.

## Что изменено

- **`MaxLeftoverPolicy`** (домен): отпечаток `SHA-256(id редактора | версия MAX |
  текст)` и ограниченный список последних 8 отпечатков. Текст, чат и получатель не
  хранятся — только хеш, как уже делал `composerShape` при обучении.
- **`MaxUiStore`**: `leftovers()/rememberLeftover()/forgetLeftover()` в общих
  настройках. Это рантайм-состояние: в код переноса настройки на новый телефон оно
  не входит.
- **`MaxUiService`**: после каждой успешной записи текста в редактор MAX — живой
  ответ и автоввод при обучении — отпечаток запоминается. Когда текст подтверждённо
  ушёл (после нажатия поле опустело), отпечаток забывается. `clearOwnLeftover`
  расширен: свой остаточный черновик узнаётся по отпечатку и очищается один раз,
  после чего сценарий продолжается. Запись в журнал — `UI_PENDING`, а не
  `UI_CHECKED`: только завершённая проверка без отправки может читаться как результат.
- **Сообщения об отказе** называют точное действие: удалить текст из поля в MAX
  вручную и повторить. Префиксы фраз сохранены — код остановки в отчёте остаётся
  `DRAFT_NOT_EMPTY` (проверяется тестом).
- **Сводка для поддержки** («Скопировать всё для поддержки» на экране «Мессенджеры»)
  теперь включает MAX-отчёт: Editor flags, Stop reason, результат обучения. Раньше
  отказ ссылался на отчёт, а единая кнопка его не собирала — причина не доезжала.

## Что не изменено

- Чужой черновик не трогается никогда: без распознанного отпечатка поле не чистится.
- Правило пустого редактора 0.8.12 не тронуто: без явного `isShowingHintText` слово
  подсказки само по себе пустотой не считается.
- Окно выбора копии MAX (8 секунд) и все остальные границы сценария не изменены.
- Черновики, оставленные сборкой 0.8.54 и старше, она не узнает — их нужно удалить
  вручную один раз; новое сообщение об отказе об этом прямо говорит.

## Проверка на телефоне

1. «Настройка MAX» → «Проверить без отправки» → дождаться `UI_CHECKED`.
2. Разрешить live и отправить тестовое сообщение на заведомо неработающую кнопку
   (или остановить сценарий после ввода) — в чате останется текст CallShift.
3. Сменить текст теста и повторить проверку: сценарий должен очистить остаточный
   черновик («Очищен остаточный черновик CallShift от прерванного сценария» в
   журнале) и дойти до обычного результата, а не до `DRAFT_NOT_EMPTY`.
4. Отдельно: начать обучение кнопки и прервать его до нажатия — текст обучения
   остаётся в чате; следующая проверка также должна его очистить.
5. «Мессенджеры» → «Скопировать всё для поддержки»: в буфере должны быть Editor
   flags и Stop reason.

Unit-тесты: `MaxLeftoverPolicyTest` — связка отпечатка с редактором/версией/текстом,
граница списка, забывание, сохранение кода остановки для новых формулировок отказа.
Работа Accessibility на телефоне пользователя по-прежнему проверяется вручную.
